Diseño de Solución

Budget Maker API — Fase de Lanzamiento

1. Resumen de la Arquitectura

El backend está diseñado como una API RESTful asíncrona implementada con Python 3.11+ y FastAPI. La persistencia de datos se gestiona en MongoDB a través del mapeador de documentos asíncrono Beanie ODM (basado en el driver asíncrono Motor).

El código está estructurado bajo las reglas de Clean Architecture, aislando las reglas de negocio del framework y los mecanismos de persistencia.

Organización de Directorios

  • app/domain/: Contiene los modelos de Beanie y esquemas de validación de Pydantic.
  • app/application/use_cases/: Orquesta la lógica del negocio. Es donde ocurren los cálculos de costos de presupuestos y la importación de Excel.
  • app/infrastructure/: Implementa el acceso a datos (repositorios de MongoDB) y adaptadores para la generación de PDF (WeasyPrint).
  • app/api/: Controladores REST y routers que exponen los endpoints al frontend desacoplado.

2. Flujo de Datos y Conexión de Capas

Para asegurar el desacoplamiento, la capa de presentación (routers de FastAPI) no interactúa directamente con los modelos de MongoDB. El flujo sigue el siguiente patrón:

Request HTTP ──> FastAPI Router ──> UseCase (Inyectado) ──> Repository ──> Beanie (MongoDB)

La inyección de dependencias se realiza mediante la utilidad Depends de FastAPI en app/api/dependencies.py.

3. Detalle de Diseño por Característica (v1)

3.1 Configuración Global Unificada (AD-1)

Se rediseña la colección global_config para almacenar un único documento fuertemente tipado en base de datos. Esto simplifica las lecturas en memoria y la coherencia del tipado:

class GlobalConfig(Document):
    tax_rate: float
    link_ttl_minutes: int
    show_product_photos_in_pdf: bool
    company_name: str
    company_subtitle: str
    company_logo_path: str | None
    payment_methods: list[str]

3.2 Carga de Imágenes de Productos (AD-3)

Para evitar saturar la base de datos con binarios o codificación Base64, se adopta el almacenamiento local en un volumen montado de Docker:

  1. El frontend envía la imagen al endpoint POST /api/v1/media/upload.
  2. El backend valida que sea PNG o JPG, la escribe en la carpeta física /uploads y retorna la ruta relativa /uploads/nombre_archivo.png.
  3. Al crear o editar el producto, el backend guarda esta ruta relativa dentro del campo images: list[str] de MongoDB.

3.3 Buscador Parcial e Importación de Tags (AD-2)

El buscador realiza consultas con expresiones regulares ($regex) e ignore-case de MongoDB sobre el SKU, nombre y tags de productos. Para las etiquetas importadas desde Excel, se procesará una columna separada por comas y se transformará en lista de strings antes de guardarse.

4. Generación de PDFs con WeasyPrint

El renderizador de PDF compila plantillas HTML escritas en Jinja2. Las directivas de estilo aplicadas garantizan lo siguiente:

  • El membrete se muestra en la cabecera de todas las páginas de manera repetitiva mediante la regla CSS de WeasyPrint: @page { @top-center { content: flow(header_membrete); } }.
  • La altura del membrete está acotada al 15% de la página para resguardar la consistencia de la presentación.
  • Las imágenes se cargan dinámicamente desde el sistema de archivos local de `/uploads` y se ocultan/muestran de forma fluida reajustando la grilla CSS de la tabla del presupuesto según la configuración del administrador.
